# 架构决策记录

> 本文件是后续修改本项目时**第一个应该读的文件**。改动前先确认你要动的模块属于哪一层，
> 不同层的严谨度要求不同。

## 一句话定位

一款面向 FPS 的手柄摇杆熟练度训练器。与 Aim Lab 这类"练枪软件"的区别在于：
本项目的**主体是手感参数本身**（死区、响应曲线、辅助瞄准），训练场景只是验证参数的手段。
因此参数管线是核心域，场景与渲染是支撑设施。

## 分层与模式决策

| 模块 | 分类 | 复杂度类型 | 模式决策 | 什么情况下该推翻这个决策 |
|---|---|---|---|---|
| `core/input` 输入管线 | **核心域** | 领域复杂 | 纯函数 + 值对象（`Resource`），零 `Node` 依赖，TDD | 如果曲线只剩线性一种，就不值得独立模块 |
| `core/aim` 辅助瞄准 | **核心域** | 领域复杂 | 三种机制拆成独立可组合的纯函数，TDD | 如果只保留一种机制，可以内联进玩家控制器 |
| `core/stats` 成绩统计 | 支撑 | 简单 | 直接聚合，无测试 | 如果引入排名/趋势分析 |
| `game/*` 场景与靶机 | 支撑 | 技术性 | 直接用 Godot 节点，薄封装 | — |
| `ui/*` 参数面板 | 支撑 | 简单 | schema 驱动 + 少量自绘 `Control` | — |

## 最重要的一条约束

**`core/` 下的任何脚本都不允许 `extends Node`，也不允许引用 `game/` 或 `ui/` 里的任何东西。**

理由有三个，按重要性排序：

1. **可测性**。手感 bug 的表现是"感觉不对"，肉眼几乎无法定位。只有当曲线和辅助瞄准是
   "输入数值 → 输出数值"的纯函数时，才能用单元测试把不变量钉死（曲线必须单调、
   死区边界必须连续、辅助强度为 0 时必须完全等价于关闭）。这些不变量一旦破坏，
   在游戏里要花几十分钟才能察觉，在测试里是 0.1 秒。
2. **可调参**。参数工具的价值在于反复试。纯函数意味着可以写脚本批量扫参数、对比曲线，
   不必每次都启动 3D 场景。
3. **可移植**。将来若要把这套手感模型搬去别的引擎，`core/` 是可以整体搬走的。

违反这条约束的代价是不可逆的：一旦核心域里出现了 `get_node()`，测试就跑不起来了，
之后所有人都只能靠手感调参。

## 坐标与单位约定

模块之间传递数值时，单位混淆是这类项目最常见的 bug 来源，因此统一约定如下，
`core/` 内所有函数的文档注释都必须显式声明自己遵守此约定：

- **摇杆原始输入**：`Vector2`，各轴 `-1..1`，`+x` 向右、`+y` 向下（沿用手柄硬件约定）。
- **视角速率与角度**：一律用**度**和**度/秒**，不用弧度。`yaw` 向右为正，`pitch` 向上为正。
  （注意这里 `pitch` 的正方向与输入的 `+y` 相反，符号翻转只发生在 `StickProcessor` 内部一处。）
- **时间**：秒。
- **角度误差 / 气泡半径**：度。

## 辅助瞄准的建模依据

参考 COD 与 Apex 的公开行为，把辅助瞄准拆成三种**互相独立**的机制。
拆开而不是做成一个"辅助强度"滑块，是因为这三者的手感差异极大，
而训练的目的恰恰是让使用者分辨出自己依赖的是哪一种：

| 机制 | 效果 | 典型来源 |
|---|---|---|
| 减速 / 粘滞 | 准星扫过目标时降低转速，让人更容易停在目标上 | 两作都有，Apex 称 slowdown |
| 旋转跟枪 | 摄像机自动跟随目标的**视野角速度**，是"自动跟枪"感的主要来源 | Apex 最显著（需移动输入才触发），COD 亦有 |
| 磁吸 | 准星被持续拉向目标中心 | COD 更明显 |

`AimAssistConfig` 提供 COD 风格与 Apex 风格两套预设，本质上只是这三个机制的不同配比，
使用者可以在预设基础上继续自定义。

## 刻意不做的事

- **ECS**：靶机数量在几十个量级，节点树完全够用，引入 ECS 只会增加理解成本。
- **状态管理框架**：参数就是一个 `Resource`，Godot 自带序列化，够了。
- **后端 / 账号**：成绩存 `user://`，本地即可。
- **武器系统 / 后坐力**：训练目标是摇杆控制，后坐力会污染变量。将来若要练压枪再加。
